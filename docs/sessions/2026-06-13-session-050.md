## Work Completed

### Real Shinka smoke test (new `~/projects/revolver-demos` repo + dedicated conda env)

- Built a separate demos repo (git) and a dedicated `revolver-demos` conda env (Py 3.12, Revolver installed editable with `[shinka]`), keeping the `shinka-spike` reference env clean.
- Authored a multi-instance Euclidean **TSP** demo (`problems/tsp`): NN baseline in an EVOLVE-BLOCK, `evaluate_instance()` scoring `nn_length/tour_length`, 5×25-city dataset; verified the score gradient (2-opt → 1.02–1.32) before any run.
- Registered project/version/dataset/LLM; validated dry-run; ran 3 real runs against the Gemini API (key via gitignored `.env`).
  - **Run 1** `gemini-2.5-flash` (2 it): all patches rejected — wrong patch format ("Could not extract code").
  - **Run 2** `gemini-2.5-pro` (10 it): 81 LLM calls all returning `None` content — Gemini thinking-token trap (revolver task 120) reproduced on the Shinka backend.
  - **Run 3 (working)** `gemini-3-flash-preview` + `--max-tokens 16384` + `--config-override evo_config.max_patch_attempts=10` (10 it): **9 evolved children, best_score 1.213 = +21% vs baseline**, 0 failures.
- **Root cause diagnosed** against ShinkaEvolve's own example configs: Revolver's `ShinkaBackend.build_config()` under-projects `max_tokens` (defaults to Shinka's 4096), `max_patch_attempts` (defaults to 1), and never sets `reasoning_efforts` — vs Shinka's examples (16384 / 10 / per-provider reasoning).

### 🔴 Critical finding — cost/token under-reporting (~20×)

- Real Google bill **€2.56** across the 3 runs vs Revolver's reported **~$0.11**. Two compounding layers: (a) `collect_token_usage()` counts only stored `programs` rows (misses failed proposals + non-stored attempts); (b) **Gemini thinking output tokens are billed but uncaptured** — run 3 reported 8,416 completion tokens vs ~500K output tokens billed by Google (console charts). Tension exposed: the `max_tokens 16384` fix that cured empty-content is also what inflates thinking-token cost; `reasoning_efforts` (unexposed) is the missing cost lever.
- All findings journaled in `revolver-demos/ISSUES.md`.

### Claude Max subscription via Agent SDK — explored, ToS-verified, scoped as a side project

- Concept: a local HTTP shim exposing an Ollama/OpenAI-compatible API backed by the Claude Agent SDK on Max OAuth, registered in Revolver via `llm add --source local`.
- Reviewed the user's own `MateoTTR/bard-ai` (private): its `src/main/sdk/` already solves the hard part (OAuth-Max via unset `ANTHROPIC_API_KEY` → `~/.claude/.credentials.json`; single-turn `query()` with `tools:[]`, `maxTurns:1`; `total_cost_usd` returned). The only missing piece is the HTTP layer.
- **ToS verified against primary sources** (code.claude.com legal-and-compliance + support article 15036540): first-party/own-subscription/private use is the intended OAuth path; the prohibition targets third-party routing of *other users'* credentials; constraint is "ordinary, individual usage"; from **2026-06-15** subscription Agent SDK/`claude -p` usage draws a separate monthly Agent SDK credit (Pro $20 / Max 5x $100 / Max 20x $200). A background research agent's initial "blocked" verdict was an overread, corrected against the sources.
- Spun off a dedicated project folder `~/projects/claude-ollama-bridge/` with a self-contained `CLAUDE.md` handoff (the revolver-scoped memory is not visible from another folder), so it can be developed in a fresh session.
