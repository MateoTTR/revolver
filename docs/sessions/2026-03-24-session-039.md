## Work Done

### OpenEvolve Architecture Analysis

Thorough investigation of OpenEvolve source code and AlphaEvolve paper (DeepMind 2025):

- **Evolution loop**: 1 iteration = 1 parent → 1 LLM call → 1 child. No batch generations.
- **Islands**: 5 by default, each with its own MAP-Elites grid. Migration every 50 iterations (ring topology).
- **MAP-Elites**: Default dimensions `complexity` (len(code) in chars) and `diversity` (fast approx, not Levenshtein). `feature_bins=10` → 100 cells per island. Custom dimensions possible via evaluator metrics.
- **LLM prompt content**: Parent code + fitness + top 3 programs (full code) + 5 inspirations (3-tier: best + elites + diverse from nearby cells) + execution artifacts. Does NOT see evaluator code or dataset instances.
- **Parallelism**: `ProcessPoolExecutor` with N workers. Each worker has its own LLM client. Multiple LLM calls in parallel, but Ollama serializes them on single GPU.
- **50 iterations analysis**: Severely under-dimensioned — ~10 programs/island, 1 migration, MAP-Elites grid half-empty. Closer to random search than real evolution.
- **AlphaEvolve vs FunSearch**: Diff-based (not full rewrite), ensemble multi-LLM (Flash 80% + Pro 20%), rich prompt context, thousands not millions of samples needed.

## Key Decisions

- **`solution diff` exit codes**: Follow Revolver convention (0=success, 1=error), not `diff(1)` convention
- **`--rank` on extract**: Remove from CLI, hardcode rank=1. Keep in domain layer and DB for future top-K support.
- **`temperature`**: Add both as LLMEntry field (like max_tokens) AND as `--temperature` flag on `revolver run` (CLI overrides registry)
- **`--config-override` JSON support**: Parse `[...]` and `{...}` via json.loads to unblock feature_dimensions
- **S9-18 (tuning guide)**: Write in main context using session knowledge, not delegate to agent
- **P2 (top-K) excluded**: Depends on OpenEvolve upstream, architecture already ready (solution extract --rank N)
