# Revolver — Concept of Operations (ConOps)

**Version**: 0.3 — Consolidated after full user review
**Date**: 2026-03-09
**Status**: Accepted

---

## 1. Purpose

Revolver is a MLOps CLI platform that orchestrates [OpenEvolve](https://github.com/algorithmicsuperintelligence/openevolve) to enable domain experts to define optimization problems, manage LLMs (local and remote), version problems and datasets, generate solutions via LLM-guided evolution, and benchmark results with full traceability.

### 1.1 Value Proposition

OpenEvolve provides the core evolutionary loop for LLM-guided code optimization. Revolver adds the **operational layer** that OpenEvolve lacks:

| Capability | OpenEvolve | Revolver |
|---|---|---|
| LLM lifecycle management | Manual setup, URL in YAML | Download, deploy, start/stop, GPU management |
| LLM registry | Per-run YAML config | Centralized catalog with credentials |
| Problem versioning | None (files on disk) | Explicit versioning with immutable snapshots |
| Dataset management | Hardcoded in evaluator | Named, versioned, split (train/eval), decoupled from evaluator |
| Solution traceability | Partial (checkpoints) | Full: problem version + dataset + LLM + config → solution |
| Benchmarking | Single run only | Multi-solution comparison on same evaluation dataset |
| Cost metrics | None | Generation time, per-instance compute time, API cost |
| Result export | Raw logs + checkpoints | Structured export (CSV, JSON) with metadata |
| Run resume | Checkpoint-based (manual) | Integrated resume with full context preservation |

## 2. Stakeholders and Personas

### 2.1 Primary Persona: Domain Expert

**Profile**: An expert in a specific optimization domain (scheduling, combinatorial optimization, logistics, etc.) who has basic knowledge of LLMs and a general understanding of OpenEvolve's evolutionary approach.

**Characteristics**:
- Strong expertise in their problem domain
- Can write Python code for problem definition and evaluation
- Has only basic notions of LLMs — does not want to manage infrastructure details
- Wants to focus on problem formulation and result analysis, not on tooling
- Works on a single machine with a powerful GPU and access to remote LLM APIs

**Goals**:
- Define an optimization problem once, iterate on its formulation
- Generate high-quality solutions using different LLMs and datasets
- Compare solutions objectively with rigorous benchmarks
- Track what produced each solution (reproducibility)
- Export results for publication or reporting

## 3. Operational Environment

### 3.1 V1 Target Environment

- **Machine**: Single workstation with a high-end NVIDIA GPU (e.g., RTX 5090, 32 GB VRAM)
- **OS**: Linux (primary), WSL2 supported
- **GPU usage**: Local LLM inference via Ollama or vLLM
- **Network**: Required for remote LLM APIs (Anthropic, Google, OpenAI)
- **LLM credentials**: Environment variables (standard approach, compatible with OpenEvolve)

### 3.2 LLM Backends

All LLMs must expose an **OpenAI-compatible API** endpoint. This is an OpenEvolve constraint that Revolver inherits.

| Backend | Example | How It Works |
|---|---|---|
| Anthropic Claude | claude-opus-4-6 | Native OpenAI-compatible endpoint |
| Google Gemini | gemini-2.5-pro | OpenAI-compatible endpoint |
| OpenAI | gpt-4o, o3 | Native |
| Local (Ollama) | llama3, codestral | Ollama serves OpenAI-compatible API locally |
| Local (vLLM) | any HuggingFace model | vLLM serves OpenAI-compatible API locally |

### 3.3 Concurrency Model (V1)

- **Remote LLM runs**: Can execute in **parallel** (no local resource conflict)
- **Local LLM runs**: Execute **sequentially** (single GPU, one model at a time)
- **Mixed**: Local runs are queued; remote runs can proceed in parallel alongside

## 4. Key Concepts and Data Model

### 4.1 Project

A **Project** is the top-level organizational unit in Revolver. It represents a single optimization domain (e.g., "job-shop scheduling", "vehicle routing", "bin packing"). Everything related to that domain lives within the project.

A project contains:
- **Problem** (with versions): the optimization problem definition
- **Datasets** (with versions): training and evaluation instance collections
- **Solutions**: evolved programs generated by OpenEvolve runs
- **Benchmarks**: evaluation results comparing solutions
- **Store**: a project-local `.revolver/` directory holding immutable snapshots and the SQLite database

**Project structure on disk**:
```
scheduling-optimizer/           # Project root (user's working directory)
├── .revolver/                  # Internal store (managed by Revolver, do not edit)
│   ├── revolver.db             # SQLite database (metrics, lineage, metadata)
│   ├── problem/                # Immutable problem version snapshots
│   │   ├── v1.0/
│   │   │   ├── initial_program.py
│   │   │   ├── evaluator.py
│   │   │   ├── config.yaml
│   │   │   ├── problem.md      # Optional problem description
│   │   │   └── manifest.yaml   # Hash, timestamp, message
│   │   └── v1.1/
│   ├── datasets/               # Dataset registrations (reference + hashes)
│   │   ├── train-small/
│   │   │   └── manifest.yaml   # Path, hashes, instance count, split, compat
│   │   └── eval-benchmark/
│   ├── runs/                  # Evolution runs (physical artifacts)
│   │   ├── <run-id>/
│   │   │   ├── manifest.yaml  # Run metadata + lineage
│   │   │   ├── config.yaml    # OpenEvolve config used
│   │   │   ├── _revolver_evaluator.py  # Generated wrapper
│   │   │   ├── oe-checkpoint/ # OpenEvolve checkpoint for resume
│   │   │   └── programs/      # Stored programs (rank-1 auto-promoted, others extractable)
│   │   │       ├── rank-1.py
│   │   │       ├── rank-2.py
│   │   │       └── rank-3.py
│   │   └── locks/             # Lock files for active runs
│   │       └── <run-id>.lock
├── initial_program.py          # Mutable working copy
├── evaluator.py                # Mutable working copy
├── config.yaml                 # OpenEvolve config (mutable)
├── problem.md                  # Optional problem description (free-form markdown)
├── project.yaml                # Project metadata (name, description, domain)
└── data/                       # User's raw data (not managed by Revolver)
    ├── instances-small/
    └── instances-eval/
```

This project-local approach means:
- Each project is **self-contained** — no cross-project pollution
- The `.revolver/` store travels with the project (can be git-versioned or backed up)
- Multiple projects on the same machine are fully independent
- LLMs are managed **globally** (see 4.6) since they are shared across projects

### 4.2 Problem

A **Problem** is the user's optimization problem definition within a project. It consists of:

- **Initial program**: The starting code that OpenEvolve will evolve. Contains `EVOLVE-BLOCK` markers delimiting what can be modified. **Can be any language** (Python, C++, Rust, etc.).
- **Evaluator**: A Python file with an `evaluate(program_path) -> dict[str, float]` function. Must be able to work with any dataset (not hardcoded). Reads the active dataset location from an environment variable set by Revolver.
- **Problem description** (optional): A free-form markdown file (`problem.md`) that describes the optimization problem in natural language. When present, its content is injected into the OpenEvolve system prompt during `revolver run` to give the LLM structured domain knowledge about the problem.
- **Metadata**: Name, description, domain, objectives description (stored in `project.yaml`).

A Problem can have multiple **Versions**. Each version is an **immutable snapshot** of the initial program + evaluator + config, stored in `.revolver/problem/`. Once versioned, the snapshot cannot be modified — the user works on a mutable working copy and creates new versions when ready.

**Language agnosticism**: Revolver does not compile or execute the evolved program directly. The evaluator is responsible for everything: compilation (if needed), execution, measurement, and scoring. For non-Python programs, the evaluator typically uses `subprocess` to compile and run the evolved code. Revolver only stores the source code and passes it through to OpenEvolve.

### 4.3 Dataset

A **Dataset** is a collection of problem instances used for training (solution generation) or evaluation (benchmarking).

**Structure**:
- A dataset is a **directory** containing instances
- Each instance is a **file or subdirectory** within the dataset directory
- Revolver is **format-agnostic**: it does not inspect instance contents
- The evaluator is responsible for reading instances in the correct format

**Properties**:
- **Name**: User-defined identifier
- **Split**: `train` (used during OpenEvolve evolution) or `eval` (used for benchmarking)
- **Compatibility**: Declared compatible with one or more Problem versions
- **Instance count**: Automatically computed by Revolver (count of top-level entries)

**Storage strategy**: Datasets are registered by **reference**, not copied into the store. Revolver records:
- The **original path** to the dataset directory
- A **SHA-256 hash** of each instance (file content hash or directory tree hash)
- A **global hash** of the entire dataset

At usage time (`revolver run`, `revolver eval`, `revolver benchmark`), Revolver **verifies integrity** by recomputing hashes and comparing to the registered values. If the data has changed, Revolver warns the user. This avoids duplicating potentially large datasets while still guaranteeing traceability.

For small datasets or critical reproducibility needs, the user can force a full copy with `revolver dataset add --snapshot`, which copies all instance files into `.revolver/datasets/<name>/snapshot/`.

### 4.4 Instance Injection Mechanism

To decouple the evaluator from specific datasets, Revolver uses an **environment-based injection**:

1. During an OpenEvolve run (training), Revolver sets:
   - `REVOLVER_DATASET_DIR` → path to the active training dataset
   - `REVOLVER_INSTANCE_LOG` → path to SQLite side-channel DB (optional, for per-instance visibility)
   - `REVOLVER_EVAL_LOG` → path to evaluator log file (optional)

2. During standalone evaluation or benchmarking, Revolver iterates over instances in the evaluation dataset, setting for each invocation:
   - `REVOLVER_INSTANCE_PATH` → path to the current instance file
   - `REVOLVER_INSTANCE_ID` → identifier of the current instance

3. The evaluator reads these variables to locate data. This approach:
   - Preserves OpenEvolve's `evaluate(program_path)` interface
   - Lets the evaluator work with any dataset without code changes
   - Gives Revolver per-instance visibility for detailed metrics

**Dual-mode evaluator**: The evaluator must support two operating modes:
- **Single-instance mode** (for Revolver eval/benchmark): `REVOLVER_INSTANCE_PATH` is set → evaluate the program on this one instance, return metrics for it
- **Aggregated mode** (for OpenEvolve training runs): `REVOLVER_DATASET_DIR` is set but `REVOLVER_INSTANCE_PATH` is not → iterate over all instances internally, return an aggregated `combined_score`

**Note**: Revolver must provide example evaluators and documentation showing both modes, including examples for non-Python programs (C++, Rust) demonstrating compilation in the evaluator.

### 4.5 Metrics and Objectives

The evaluator returns a `dict[str, float]` where each key is a metric or objective. All values must be numeric (float).

**Key conventions**:
- `combined_score`: Required by OpenEvolve as the primary fitness metric (always **maximized**). The user computes this from their objectives (e.g., `1.0 / makespan` for minimization).
- Other keys: Domain-specific raw metrics (e.g., `makespan`, `total_cost`, `quality`). These are stored and reported as-is.

**Direction of objectives**: In V1, Revolver is **agnostic** — it reports raw statistics (mean, min, max, percentiles, std) without knowing which direction is "better". The user interprets their own metrics. A future version may add direction metadata in `project.yaml`.

**Multi-objective**: Multiple keys in the dict naturally support multi-objective problems. Benchmark statistics are computed **per metric key**.

### 4.6 Solution

A **Solution** is a **lightweight reference** to a program within a Run. It is a database row with `(run_id, rank)` and an optional alias. A Solution does **not** own a filesystem directory.

- **Identity**:
  - Auto-generated ID
  - Optional user-defined alias for readability
  - Rank within the parent run (e.g., #1 = best program)
- **Metrics**: Best score from the evolution run
- **Program path** (derived): `.revolver/runs/<run_id>/programs/rank-<N>.py`
- **Lineage**: Inherited from the parent Run (problem version, dataset, LLM, config, generation time, iterations)
- **Run reference**: Links to the Run that produced it (`run_id`)
- **Creation**: The rank-1 solution is auto-created by `revolver run`. Additional solutions can be extracted on demand via `revolver solution extract --run <id> --rank <N>`, which promotes a stored program to a first-class solution with post-extraction training evaluation.

A **Run** is the first-class physical entity that owns all artifacts from an OpenEvolve evolution:
- **Programs**: All top-ranked evolved programs stored in `.revolver/runs/<run_id>/programs/` (from OpenEvolve output). Only the best (rank-1) is auto-promoted to a solution; others are available for inspection and on-demand extraction.
- **Checkpoint**: OpenEvolve checkpoint for potential resume, stored in `.revolver/runs/<run_id>/oe-checkpoint/`
- **Config**: The OpenEvolve config used for this run
- **Wrapper**: The generated evaluator wrapper (`_revolver_evaluator.py`)
- **Manifest**: Full lineage metadata (problem version, dataset, LLM, iterations, generation time, status)
- **Token usage**: Total prompt and completion tokens consumed during the evolution (tracked via a transparent proxy). Combined with optional LLM pricing to estimate cost per run.

### 4.7 Benchmark

A **Benchmark** is the evaluation of one or more Solutions against a single evaluation Dataset.

**What it produces per solution**:
- Aggregate statistics: mean, min, max, p10, p50, p90, std deviation
- Per-objective breakdown (if multi-objective)
- Compute time per instance (wall clock)
- Total evaluation time

**What it enables**:
- Compare solutions generated by different LLMs
- Compare solutions generated with different training datasets
- Compare solutions from different problem version evolutions
- Identify which solution performs best overall and on which instance types

### 4.8 LLM

An **LLM** in Revolver is a registered model available for use in OpenEvolve runs.

**Types**:
- **Remote**: API-based (Anthropic, Google, OpenAI). Configured with provider, model name, API key env var.
- **Local**: Served locally via Ollama or vLLM. Revolver manages download, deployment, start/stop, GPU allocation.

**Registry** stores:
- Name (user-facing identifier)
- Provider / source (e.g., `anthropic`, `huggingface:meta-llama/Llama-3-70B`)
- API base URL (auto-configured for local models)
- Model parameters (context window, etc.)
- Status (downloaded, running, stopped — for local models)

## 5. User Workflows

### 5.1 Workflow 1 — Setup LLMs (global)

LLM management is **global** (not per-project), since models are shared resources.

```
# Register a remote LLM
revolver llm add claude-opus \
  --provider anthropic \
  --model claude-opus-4-6

# Register and deploy a local LLM
revolver llm add codestral-local \
  --source huggingface \
  --model mistralai/Codestral-22B-v0.1

# Check available LLMs
revolver llm list

# Start a local model (allocates GPU)
revolver llm start codestral-local

# Check status
revolver llm status
```

### 5.2 Workflow 2 — Create a Project and Define a Problem

```
# Initialize a new project
revolver project init scheduling-optimizer
# → Creates project directory:
#   scheduling-optimizer/
#     .revolver/              (internal store, empty)
#     initial_program.py      (template with EVOLVE-BLOCK markers)
#     evaluator.py            (template with REVOLVER_DATASET_DIR pattern)
#     config.yaml             (OpenEvolve defaults)
#     project.yaml            (metadata: name, description, domain)

cd scheduling-optimizer

# User edits the files to define their problem...
# User prepares data in data/ directory...
```

### 5.3 Workflow 3 — Test the Problem Before Versioning

Before creating an immutable version, the user **validates** that the evaluator works correctly with the data. This catches bugs early: parsing errors, missing dependencies, wrong return format, etc.

```
# Test the evaluator on a single instance (smoke test)
revolver problem test \
  --instance ./data/instances-small/instance_001.json
# → Runs evaluate(initial_program) with REVOLVER_INSTANCE_PATH set
# → Shows: returned metrics, execution time, any errors/warnings
# → Example output:
#   ✓ Evaluator loaded successfully
#   ✓ Instance: instance_001.json
#   ✓ Metrics returned: {"makespan": 142.5, "combined_score": 0.35}
#   ✓ Execution time: 0.8s
#   ✓ No errors

# Test on all instances in a dataset directory (full validation)
revolver problem test \
  --dataset ./data/instances-small/
# → Iterates over all instances, reports per-instance success/failure
# → Example output:
#   Testing 50 instances from ./data/instances-small/
#   ✓ 48/50 instances passed
#   ✗ instance_023.json — KeyError: 'duration' in evaluator.py:45
#   ✗ instance_041.json — Timeout after 300s
#   Summary: 48 passed, 2 failed, mean time: 1.1s, max time: 4.2s

# Test with verbose output for debugging
revolver problem test \
  --instance ./data/instances-small/instance_023.json \
  --verbose
# → Shows full stack trace, stdout/stderr, returned dict
```

This workflow is **essential** before:
- Creating a problem version (`revolver problem version`)
- Registering a dataset (`revolver dataset add`)

Revolver does not enforce this (the user can skip testing), but the documentation and templates strongly recommend it.

### 5.4 Workflow 4 — Version the Problem and Register Datasets

Once testing passes, the user locks down the problem definition and datasets:

```
# Create an immutable problem version
revolver problem version --tag v1.0 --message "Initial formulation"

# Register a training dataset (creates immutable snapshot)
revolver dataset add \
  --name train-small \
  --split train \
  --path ./data/instances-small/ \
  --compatible-with v1.0

# Register an evaluation dataset
revolver dataset add \
  --name eval-benchmark \
  --split eval \
  --path ./data/instances-eval/ \
  --compatible-with v1.0

# Inspect
revolver dataset info train-small
# → 50 instances, split: train, compatible with: v1.0

# Later, after refining the problem:
revolver problem version --tag v1.1 --message "Refined objective function"

# Update dataset compatibility (if the data is still valid for v1.1)
revolver dataset update train-small --add-compatible-with v1.1

# List everything
revolver problem versions
revolver dataset list
```

### 5.5 Workflow 5 — Generate a Solution

```
# Run OpenEvolve to generate a solution
revolver run \
  --version v1.1 \
  --llm claude-opus \
  --dataset train-small \
  --iterations 200 \
  --alias "claude-small-v1.1"

# Monitor a running evolution
revolver run status

# Resume an interrupted run (creates a new run linked to the original)
revolver run resume --run <run-id>

# List all runs (filter by version, LLM, status)
revolver run list

# Show detailed run info (solutions, resume chain)
revolver run info <run-id>

# List generated solutions
revolver solution list
```

**End-to-end walkthrough**: See [user-story-e2e.md](../specs/user-story-e2e.md) for a concrete scenario covering all workflows from project creation to benchmark export.

### 5.6 Workflow 6 — Evaluate a Single Solution

```
# Evaluate a solution on an evaluation dataset
revolver eval \
  --solution claude-small-v1.1 \
  --dataset eval-benchmark

# View results
revolver eval results --solution claude-small-v1.1
# → Objective: mean=0.87, min=0.62, max=0.95, p90=0.93, std=0.08
#   Compute time: mean=1.2s, max=4.5s, total=60s
#   Instances: 50/50 solved
```

### 5.7 Workflow 7 — Benchmark Multiple Solutions

```
# Compare multiple solutions
revolver benchmark \
  --solutions claude-small-v1.1 gemma-small-v1.1 claude-large-v1.1 \
  --dataset eval-benchmark

# View benchmark results
revolver benchmark results --latest
# → Table comparing all solutions:
#   Solution              | mean  | min  | max  | p90  | std  | gen_time | eval_time
#   claude-small-v1.1     | 0.87  | 0.62 | 0.95 | 0.93 | 0.08 | 2h15m    | 60s
#   gemma-small-v1.1      | 0.82  | 0.55 | 0.91 | 0.89 | 0.11 | 1h30m    | 55s
#   claude-large-v1.1     | 0.91  | 0.70 | 0.97 | 0.95 | 0.06 | 3h45m    | 62s

# Export results
revolver benchmark export --latest --format csv --output results.csv
```

## 7. Immutability and Integrity

### 7.1 Problem Versioning

When the user creates a problem version (`revolver problem version`), Revolver:

1. **Copies** the initial program, evaluator, config, and `problem.md` (if present) into `.revolver/problem/<tag>/`
2. **Computes a SHA-256 hash** of the snapshot contents
3. **Records** the hash, timestamp, and user message in `manifest.yaml`

Problem versions are **full snapshots** (code is small) — the user can freely modify their working copy.

### 7.2 Dataset Registration

When the user registers a dataset (`revolver dataset add`), Revolver:

1. **Records the original path** to the dataset directory
2. **Computes a SHA-256 hash** per instance and a global hash
3. **Stores** path, hashes, instance count, split, and compatibility in `.revolver/datasets/<name>/manifest.yaml`
4. Data files are **not copied** by default (reference-only)

Integrity is **verified at usage time** (run, eval, benchmark). If hashes don't match, Revolver warns. The user must re-register the dataset if data has changed.

For full reproducibility, `revolver dataset add --snapshot` copies all files into the store.

### 7.3 Recommended Workflow: Test Before Version

The `revolver problem test` command is designed to be run **before** versioning. The recommended flow is:

1. Edit `initial_program.py` and `evaluator.py` (mutable working copies)
2. Prepare instance data in `data/`
3. Run `revolver problem test --dataset ./data/instances/` to validate
4. Fix any issues, re-test
5. Once all tests pass: `revolver problem version --tag v1.0`
6. Then: `revolver dataset add --name train-small --path ./data/instances/`

Revolver does not enforce this order, but documentation and templates strongly recommend it.

### 7.4 Dataset Compatibility

Datasets declare compatibility with Problem versions. Revolver **warns** (but does not block) if a user attempts to use a dataset with an incompatible version. This balances safety with flexibility.

## 9. Scope Summary — V1

### In Scope
- Single CLI binary (`revolver`) with subcommands
- **Project** as top-level organizational unit (project-local `.revolver/` store)
- LLM registry (remote + local) — global (`~/.revolver/`)
- Local LLM lifecycle management (download, start, stop, GPU detection, VRAM management)
- Problem definition (Option A: user provides full OpenEvolve-compatible files)
- **Problem testing** (`revolver problem test`) — validate evaluator + data before versioning
- Problem versioning with immutable snapshots
- Dataset management with train/eval split and declared compatibility
- Dataset compatibility update (add/remove compatible versions)
- Instance injection via environment variables
- Solution generation via OpenEvolve orchestration
- Run resume (OpenEvolve checkpoint integration)
- Standalone solution evaluation with aggregate statistics (mean, min, max, percentiles, std)
- Multi-solution benchmarking
- Full traceability (problem version, dataset, LLM, config → solution)
- Cost metrics (generation time, per-instance compute time, token usage, estimated API cost)
- Result export (CSV, JSON)
- Sequential local LLM runs, parallel remote LLM runs
- Automatic rank-1 solution creation, on-demand extraction for other ranks
- SQLite for metrics + YAML for configs
- Example problems and evaluators demonstrating the instance injection pattern (Python + non-Python examples)
- Dataset registration by reference (hash-only) with optional `--snapshot` for full copy

### Out of Scope (V1)
- Web dashboard / visualization
- Multi-machine / cluster execution
- Parallel local LLM runs
- Problem templates by domain (Option C)
- Automatic evaluator generation
- API cost estimation / budgeting
- User authentication / multi-tenant

## 10. Open Questions

- [x] **OQ-01**: Exact local LLM management tool — **Resolved: Ollama** (9x faster than vLLM, 4x less VRAM via quantization, native OpenAI-compatible API, clean lifecycle management) (→ ADR-001)
- [x] **OQ-02**: Primary programming language for Revolver itself — **Resolved: Python >= 3.11** (→ ADR-002)
- [x] **OQ-03**: CLI framework choice — **Resolved: Typer >= 0.21** (→ ADR-003)
- [x] **OQ-04**: Internal store location — **Resolved**: project-local `.revolver/` for project data, global `~/.revolver/` for LLMs
- [x] **OQ-05**: How to handle OpenEvolve's evaluator iteration vs Revolver's instance injection during training runs — **Resolved: A+B hybrid strategy** — env var injection (`REVOLVER_DATASET_DIR`) as core mechanism + optional SQLite side-channel (`REVOLVER_INSTANCE_LOG`) for per-instance visibility. Callable evaluator (Strategy C) rejected (fork-dependent, fragile). Revolver generates the wrapper evaluator; user writes only `evaluate_instance()`. (→ ADR-006, POC #12)
- [x] **OQ-06**: Exact mechanism for Revolver to control which dataset the evaluator uses during an OpenEvolve run — **Resolved: Dual-mode evaluator pattern** — `REVOLVER_DATASET_DIR` for aggregated training mode, `REVOLVER_INSTANCE_PATH` for single-instance eval/benchmark mode. `os.environ` propagates reliably to OpenEvolve worker processes. Resume requires `OpenEvolve` controller class (not `run_evolution()`). (→ ADR-006, POC #12)
- [ ] **OQ-07**: Should `revolver problem test` block versioning on failure, or just warn? (→ UX decision)
- [x] **OQ-08**: WSL2 + CUDA + RTX 5090 compatibility — **Resolved: Fully compatible** (RTX 5090 32 GB works out of the box in WSL2, no CUDA toolkit install needed, driver 595.71 forwarded via GPU-PV)

## Appendix A — OpenEvolve Interface Summary

For reference, here is how OpenEvolve defines and runs a problem natively:

**Three required inputs**:
1. `initial_program.py` — Code with `EVOLVE-BLOCK` markers
2. `evaluator.py` — Python file with `evaluate(program_path: str) -> dict`
3. `config.yaml` — LLM, evolution, population, evaluator parameters

**Run command**:
```bash
python openevolve-run.py initial_program.py evaluator.py --config config.yaml --iterations 100
```

**Key constraints**:
- Evaluator must always be Python
- Evaluator receives only `program_path` (no instance argument)
- `combined_score` is the primary fitness metric
- All LLMs must expose OpenAI-compatible API
- EVOLVE-BLOCK markers delimit what the LLM can modify

Revolver wraps this interface, adding dataset injection, versioning, and traceability without modifying OpenEvolve itself.
