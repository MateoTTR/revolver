## 1. Overview

This document details the design of the `revolver eval` commands: the default command (evaluate a solution against a dataset) and `results` (display stored evaluation results). The evaluation loop iterates over dataset instances in single-instance mode (ADR-006), calls the evaluator from the immutable problem version snapshot, and stores raw per-instance results in SQLite.

### 1.1 Key Responsibilities

| Responsibility | Description |
|---|---|
| **Input validation** | Solution exists, dataset exists, compatibility check |
| **Integrity verification** | Dataset hash check before evaluation |
| **Instance iteration** | Enumerate instances, set env vars per instance |
| **Evaluator invocation** | Call evaluator from problem version snapshot in subprocess |
| **Error isolation** | Per-instance failure does not abort the full evaluation |
| **Timeout enforcement** | Per-instance timeout via subprocess |
| **Result storage** | Raw per-instance results in SQLite (single source of truth) |
| **Aggregate computation** | Compute aggregates at display time from raw data |
| **Progress reporting** | Progress bar during evaluation |

### 1.2 Relationship with `revolver run`

The evaluation loop is also used by `revolver run` for post-run training evaluation (FR-RUN-019, [DES-005](DES-005-run-orchestration.md) §7). The core function `evaluate_solution()` is designed to be called from both `revolver eval` (CLI entry point) and `core.run._post_run_evaluation()` (internal).

> **Post-run eval persistence (U11, v0.18 — S18 / #368).** As of v0.18 the post-run path **actually
> flows through** `evaluate_solution()` (FR-RUN-019/020), closing the Task-86 residue in which
> `core.run._run_post_eval` re-implemented the loop with a hardcoded 300 s timeout and stored
> nothing (stderr-only). Consequences on the eval side, which owns the persistence contract:
> post-run training results are written to `eval_metadata`/`eval_instances` exactly like a manual
> `revolver eval` (single storage contract — immediately visible via `revolver eval results` and
> reusable by `benchmark` skip-re-eval, §7.3), and the per-instance timeout comes from the eval
> path's `timeout_s`, not a hardcoded constant. The existing-eval check (§5) applies to the
> internal caller too — `core.run` passes `force=True` (or checks for an existing eval first) so a
> resume-then-re-eval never dead-ends on the D-006-a confirmation. Failure remains **warn-only** on
> the run side, and the caller must guard against DB contention before the call (commit the
> still-open launch connection; WAL + `busy_timeout` cover the rest) since `launch_run` still holds
> its project-DB connection. Launch-side flow and error handling: DES-005 §7.

### 1.3 Backend independence and per-backend training wrappers (ADR-007)

`revolver eval` is **engine-neutral**: it runs the evaluator from the immutable problem version
snapshot against extracted program files — it never touches the evolution engine. The user-facing
evaluator contract is therefore unchanged by ADR-007: the user writes
`evaluate_instance(program_path, instance_path) -> dict[str, float]`, once, regardless of backend.

What differs per backend is the **training-time wrapper** generated by `revolver run`
(DES-005 §3, `generate_wrapper()` on the backend interface):

| Backend | Wrapper shape | Result channel |
|---|---|---|
| OpenEvolve | In-process `evaluate(program_path) -> dict` (dual-mode per ADR-006) | Return value (dict) |
| ShinkaEvolve | Subprocess CLI `evaluate.py` driven by `run_shinka_eval`, iterating `evaluate_instance()` over the dataset | Files: `metrics.json` (`combined_score` + metrics) and `correct.json` written to the results dir |

Both wrappers consume the same ADR-006 env-var inputs (`REVOLVER_DATASET_DIR`, …) and the same
user `evaluate_instance()`. The Shinka wrapper's file-based output contract is the top
silent-bug risk of the backend initiative (impact R4) — its contract tests are front-loaded in S14.

> **Numeric-only aggregation guard (B1, v0.17).** The training-time aggregation performed **inside**
> the generated wrappers (DES-005 §3.2, the OpenEvolve `_WRAPPER_TEMPLATE` mean loop) applies the
> same numeric guard as `compute_aggregates()` (§4.3): a non-numeric metric value (e.g. an `error`
> string mixed in with `combined_score`) is skipped rather than crashing the mean. The guard idiom
> `isinstance(x, (int, float)) and not isinstance(x, bool)` is shared across the Shinka wrapper, the
> OpenEvolve wrapper, and the read-time `compute_aggregates()` — B1 lives in the generated wrapper
> too, not only in the read path.

> **Reserved `instances_*` coverage keys + timeout policy (U13, v0.18 — S18 / #367).** Both
> generated wrapper templates emit `instances_valid`/`instances_total` coverage keys and record
> timed-out instances on a side-channel; the wrapper-side design (template changes, mean-loop
> exclusion, the `evaluation.on_timeout: penalize|drop` + `timeout_score` policy, the distinct
> Shinka `TimeoutError` branch) lives in **DES-005 §3.2** (FR-RUN-053/054) and is not duplicated
> here. What DES-006 owns is the **read/eval-path counterpart**: the `instances_` metric prefix is
> **reserved**, and any `instances_*` key is excluded from every aggregation Revolver performs —
> the wrapper mean loops (DES-005 §3.2) and the read-time `compute_aggregates()` (§4.3,
> FR-EVL-021 as amended). Coverage is metadata, never averaged into a score. `revolver eval`'s
> own timeout semantics are **unchanged**: an eval-loop timeout still records `status='timeout'`
> (`value` NULL) and is excluded from aggregates as before — the penalize policy applies to
> training-time fitness only. After v0.18 there are deliberately **two timeout semantics** (triage
> §3 residual): engine fitness *penalizes* timeouts (evolution pressure), post-run/manual eval
> reports honest coverage-labeled means (reporting) — the `run info` labels carry the burden
> (FR-RUN-055, DES-005 §2.5).

## 2. Command → Layer Flow

### 2.1 `revolver eval`

Evaluate a solution against an evaluation dataset.

```
CLI (cli/eval.py)
  │ Parse: --solution, --dataset, --timeout, --parallelism, --force
  ▼
Core (core/eval.py) → evaluate_solution()
  │ 1. Resolve project root                        ──► Infra: store.find_project_root()
  │ 2. Load solution metadata                       ──► Infra: db.get_solution(id_or_alias)
  │                                                     → returns solution with run_id
  │ 3. Load run metadata                            ──► Infra: db.get_run(solution.run_id)
  │                                                     → provides problem_version, llm, etc.
  │ 4. Load dataset registration                    ──► Infra: db.get_dataset(name)
  │    Quick integrity check                        ──► Core: dataset.verify_dataset_integrity()
  │    Warn if split != 'eval'                     (FR-EVL-009)
  │    Warn if not compatible with version          (FR-EVL-008)
  │ 5. Check for existing results                   ──► Infra: db.get_eval_metadata()
  │    If exists and not --force:
  │      JSON mode → raise error                   (D-006-a)
  │      Interactive → prompt confirmation          (D-006-a)
  │    If confirmed or --force → db.delete_eval()
  │ 6. Resolve program path:
  │    .revolver/runs/<run_id>/programs/rank-<N>.py
  │ 7. Resolve evaluator path:
  │    .revolver/problem/<version>/evaluator.py     (FR-EVL-003)
  │ 8. Load evaluator module                        ──► Infra: evaluator_loader.load(path)
  │ 9. Resolve dataset path                         ──► Core: dataset.resolve_dataset_path()
  │ 10. Enumerate instances:
  │     sorted(p for p in dataset_path.iterdir() if not p.name.startswith('.'))
  │ 11. Generate eval ID                            ──► generate_eval_id()
  │ 12. Evaluation loop: for each instance:
  │     a. Set REVOLVER_INSTANCE_PATH               (FR-EVL-002)
  │     b. Set REVOLVER_INSTANCE_ID
  │     c. Call evaluator in subprocess with timeout (§3)
  │     d. Collect metrics dict + wall-clock time
  │     e. Store raw result in SQLite immediately    ──► Infra: db.insert_eval_instance()
  │     f. Report progress                           ──► callback to CLI
  │ 13. Store eval metadata in SQLite               ──► Infra: db.insert_eval_metadata()
  │ 14. Return EvalResult
  ▼
Infra
  ├── store: project root, evaluator path resolution
  ├── db: read solution/run/dataset, write eval results
  ├── evaluator_loader: dynamic module loading
  └── hashing: dataset integrity verification
```

### 2.2 `revolver eval results`

Display results of a previous evaluation.

```
CLI (cli/eval.py)
  │ Parse: --solution, --dataset, --per-instance, --json
  ▼
Core (core/eval.py) → get_eval_results()
  │ 1. Resolve solution                             ──► Infra: db.get_solution(id_or_alias)
  │ 2. Query eval metadata                          ──► Infra: db.get_eval_metadata()
  │    If no results found → error:                (D-006-b)

  │       Run `revolver eval --solution X --dataset Y` first."
  │      Exit code 1
  │ 3. If --per-instance:
  │    a. Query all raw instance results            ──► Infra: db.get_eval_instances()
  │    b. Return EvalDetailResult
  │ 4. Else (aggregates):
  │    a. Query raw instance results                ──► Infra: db.get_eval_instances()
  │    b. Compute aggregates in Python              (§4)
  │    c. Return EvalSummaryResult
  ▼
Infra
  └── db: query eval_metadata, eval_instances
```

## 3. Instance Evaluation Subprocess

Each instance is evaluated in an isolated subprocess, reusing the pattern from [DES-003 §2.1.1](DES-003-problem-versioning.md).

### 3.1 Why Subprocess?

Same rationale as DES-003 DD-01:
- **Hard timeout**: `future.result(timeout=N)` followed by process termination
- **Crash isolation**: evaluator segfaults don't affect the main Revolver process
- **Clean environment**: env vars set in child don't pollute parent

### 3.2 Subprocess Execution

```python
from concurrent.futures import ProcessPoolExecutor, TimeoutError

def _evaluate_instance(
    evaluator_path: Path,
    program_path: Path,
    instance_path: Path,
    instance_id: str,
    timeout_s: int = 300,
) -> InstanceResult:
    """
    Evaluate a single instance in a subprocess.

    1. Spawn subprocess via ProcessPoolExecutor(max_workers=1)
    2. In child process:
       a. Set REVOLVER_INSTANCE_PATH = str(instance_path)
       b. Set REVOLVER_INSTANCE_ID = instance_id
       c. Import evaluator module
       d. Call evaluate(program_path) or evaluate_instance(program_path, instance_path)
       e. Return metrics dict
    3. In parent: collect result with timeout
    4. On timeout: cancel future, return InstanceResult(status="timeout")
    5. On exception: return InstanceResult(status="failed", error=str(e))
    """
```

### 3.3 Evaluator Resolution

The evaluator is loaded from the **immutable problem version snapshot**, not the mutable working copy (FR-EVL-003):

```
.revolver/problem/<version>/evaluator.py
```

This ensures evaluation results are reproducible — the evaluator code cannot change between evaluations of the same problem version.

**Dual-mode detection**: The evaluator may define either:
1. `evaluate(program_path)` — standard OpenEvolve interface (legacy), used as-is
2. `evaluate_instance(program_path, instance_path)` — Revolver-style, called directly with instance path

Detection priority (D-005-a):
1. If `evaluate()` exists → set `REVOLVER_INSTANCE_PATH` env var, call `evaluate(program_path)` (legacy mode)
2. Else if `evaluate_instance()` exists → call directly with `(program_path, instance_path)` (Revolver mode)
3. Else → error

**Rationale for priority order**: If both functions exist in the same file, `evaluate()` takes precedence because it is the "complete" implementation — the user may call `evaluate_instance()` internally from their `evaluate()`. Revolver should not bypass the user's orchestration logic by calling `evaluate_instance()` directly when `evaluate()` is available.

### 3.4 Parallelism (FR-EVL-014 — MAY)

Optional `--parallelism <n>` uses a `ProcessPoolExecutor` with `max_workers=n`:

```python
if parallelism > 1:
    with ProcessPoolExecutor(max_workers=parallelism) as pool:
        futures = {
            pool.submit(_eval_worker, evaluator_path, program_path, inst, timeout_s): inst
            for inst in instances
        }
        for future in as_completed(futures):
            instance = futures[future]
            result = future.result()  # InstanceResult
            ...
```

**Constraints**:
- Default parallelism is 1 (sequential)
- Parallelism is limited to the number of CPU cores
- Each subprocess gets its own environment (env vars are set per-worker)
- SQLite writes are safe with WAL mode (validated in POC #12 S4)

## 4. Aggregate Computation

### 4.1 Design Decision: Compute at Read Time (DD-01)

FR-EVL-006 specifies: "Compute aggregate statistics at read time from stored raw data — aggregates are not stored separately."

The initial DES-001 (v0.1) defined an `eval_results` table for stored aggregates (DM-01). Following FR-EVL-006, this was replaced by the current `eval_metadata` table (DES-001 v0.2 §3.7), which stores only evaluation session metadata — no per-metric aggregate rows.

**Decision**: Aggregates are computed in Python from raw `eval_instances` data at display time. DES-001 §3.7 defines `eval_metadata` (session metadata only), consistent with this approach.

**Rationale**:
- **Single source of truth**: raw per-instance data is the only stored data; aggregates are derived
- **Flexibility**: if aggregate formulas change (e.g., add p25/p75), no migration needed
- **Simplicity**: one table for raw data, one for metadata, instead of three (metadata + aggregates + instances)
- **Performance is acceptable**: computing aggregates from 10,000 instances in Python takes <10ms; even 100,000 instances complete in <100ms

### 4.2 Schema Reference

The definitive schema is in DES-001 §3.7–3.8. Key tables for reference:

```sql
CREATE TABLE eval_metadata (
    eval_id         TEXT PRIMARY KEY,       -- "eval-YYYYMMDD-HHMMSS"
    solution_id     TEXT NOT NULL REFERENCES solutions(id),
    dataset_name    TEXT NOT NULL REFERENCES datasets(name),
    instance_count  INTEGER NOT NULL,
    instances_solved INTEGER NOT NULL,
    eval_time_s     REAL,                   -- total wall-clock time
    user_aggregates TEXT,                   -- JSON: {"combined_score": 0.72, ...}
                                            -- NULL if evaluate_instance() mode (D-006-g)
    evaluated_at    TEXT NOT NULL            -- ISO 8601
);

CREATE UNIQUE INDEX idx_eval_unique ON eval_metadata(solution_id, dataset_name);
```

The `eval_instances` table (DES-001 §3.8) is **kept as-is** but with a simplified foreign key:

```sql
CREATE TABLE eval_instances (
    eval_id         TEXT NOT NULL REFERENCES eval_metadata(eval_id),
    instance_id     TEXT NOT NULL,
    metric_name     TEXT NOT NULL,
    value           REAL,                   -- NULL if failed/timeout
    status          TEXT NOT NULL CHECK (status IN ('solved', 'failed', 'timeout')),
    error_message   TEXT,                   -- if status != 'solved'
    compute_time_s  REAL,                   -- wall-clock time for this instance
    PRIMARY KEY (eval_id, instance_id, metric_name)
);

CREATE INDEX idx_eval_inst_eval ON eval_instances(eval_id);
```

**Note**: `idx_eval_unique` on `eval_metadata` ensures at most one evaluation per (solution, dataset). Re-evaluation replaces the previous result (DELETE old + INSERT new in a transaction).

### 4.3 Aggregate Computation Logic

```python
import statistics

def _is_numeric(x: object) -> bool:
    """Aggregate only real numbers. Exclude bool (a subclass of int) and any
    non-numeric metric value (e.g. an 'error' string). B1 guard — mirrors the
    idiom used in the generated OpenEvolve/Shinka wrappers (DES-005 §3)."""
    return isinstance(x, (int, float)) and not isinstance(x, bool)


def compute_aggregates(
    instances: list[InstanceResult],
) -> dict[str, MetricAggregate]:
    """
    Compute aggregate statistics from raw per-instance results.

    For each metric key found across solved instances:
        - mean, min, max
        - p10, p50 (median), p90
        - std (sample standard deviation; 0.0 if n=1)

    Numeric-only guard (B1): non-numeric metric values (strings such as an
    'error' field, None, bool) are skipped rather than crashing the aggregation.
    A key whose values are all non-numeric contributes no aggregate row; the
    empty-instance set is handled cleanly (returns {}).

    Reserved-prefix guard (U13, v0.18): metric keys with the reserved
    `instances_` prefix (wrapper coverage metadata, FR-RUN-053 — e.g.
    `instances_valid`/`instances_total`) are excluded from aggregation
    entirely. Coverage counts are metadata, never averaged into a score
    (FR-EVL-021 as amended; §1.3).

    Returns dict mapping metric_name → MetricAggregate.
    """
    solved = [i for i in instances if i.status == "solved"]
    if not solved:
        return {}

    # Discover all metric keys
    all_keys: set[str] = set()
    for inst in solved:
        all_keys.update(inst.metrics.keys())

    aggregates = {}
    for key in sorted(all_keys):
        # Reserved coverage keys (U13): metadata, never aggregated (FR-EVL-021).
        if key.startswith("instances_"):
            continue
        # Skip non-numeric metric values (B1): guard on each value, not just presence.
        values = [
            inst.metrics[key]
            for inst in solved
            if key in inst.metrics and _is_numeric(inst.metrics[key])
        ]
        if not values:
            continue
        values_sorted = sorted(values)
        n = len(values_sorted)
        aggregates[key] = MetricAggregate(
            mean=statistics.mean(values),
            min=min(values),
            max=max(values),
            p10=_percentile(values_sorted, 0.10),
            p50=_percentile(values_sorted, 0.50),
            p90=_percentile(values_sorted, 0.90),
            std=statistics.stdev(values) if n > 1 else 0.0,
            count=n,
        )
    return aggregates


def _percentile(sorted_values: list[float], p: float) -> float:
    """Compute percentile using linear interpolation (same as numpy default)."""
    n = len(sorted_values)
    if n == 1:
        return sorted_values[0]
    k = (n - 1) * p
    f = int(k)
    c = f + 1
    if c >= n:
        return sorted_values[-1]
    d = k - f
    return sorted_values[f] + d * (sorted_values[c] - sorted_values[f])
```

### 4.4 Legacy Global Aggregation (D-006-g)

For legacy evaluators (`evaluate()` mode), after per-instance evaluation, an additional global call is made to retrieve the user's custom aggregates (e.g., `combined_score`):

1. **Per-instance** (as before): call `evaluate()` with `REVOLVER_INSTANCE_PATH` set per instance → collects per-instance metrics → Revolver computes its own aggregates (mean, min, max, p10, p50, p90, std)
2. **Global aggregation** (new): one final call to `evaluate()` **without** `REVOLVER_INSTANCE_PATH`, **with** `REVOLVER_DATASET_DIR` set to the dataset directory → retrieves the user's custom `combined_score` and any other aggregated metrics

The result of the global aggregation call is stored in `eval_metadata.user_aggregates` as a JSON string.

For `evaluate_instance()` mode, this step is skipped (`user_aggregates = NULL`), since the Revolver-style evaluator has no built-in global aggregation mechanism.

| Evaluator mode | Per-instance step | Global aggregation step |
|---|---|---|
| `evaluate_instance()` | Direct call per instance | Not applicable |
| `evaluate()` (legacy) | Call with `REVOLVER_INSTANCE_PATH` | Call with `REVOLVER_DATASET_DIR` |

**Display**: `revolver eval results` shows both sections when user aggregates are available:
- "Revolver aggregates": computed from per-instance raw data (mean, p10, p50, p90, etc.)
- "User aggregates": raw result from the global `evaluate()` call (only in legacy mode)

## 5. Re-Evaluation Handling (D-006-a)

When evaluating a solution that already has results on the same dataset, the user must confirm or use `--force`:

```python
def evaluate_solution(
    ...,
    force: bool = False,
    json_mode: bool = False,
) -> EvalResult:
    existing = db.get_eval_metadata(solution_id, dataset_name)
    if existing:
        if json_mode and not force:
            raise EvalError("Evaluation already exists. Use --force to re-evaluate.")
        if not force:
            # Interactive confirmation
            confirm = prompt(f"Evaluation already exists for solution {solution_id} "
                           f"on dataset {dataset_name}. Re-evaluate? [y/N]")
            if not confirm:
                raise EvalAborted("Re-evaluation cancelled by user.")
        db.delete_eval(existing.eval_id)  # Cascades to eval_instances
    # Proceed with evaluation...
```

**Behavior summary**:

| Mode | `--force` | Existing results | Action |
|---|---|---|---|
| Interactive | No | Yes | Prompt confirmation (`[y/N]`) |
| Interactive | Yes | Yes | Delete and re-evaluate silently |
| `--json` | No | Yes | Error (exit code 1) |
| `--json` | Yes | Yes | Delete and re-evaluate silently |
| Any | Any | No | Proceed normally |

**Rationale**: Re-evaluation is a destructive operation (deletes previous results). Unlike the previous unconditional replace, the confirmation step protects against accidental data loss — especially in scripted pipelines where `--json` mode requires explicit `--force`. For interactive use, the prompt gives the user a chance to abort. The `--force` flag preserves scriptability for intentional re-evaluation.

Note: `revolver eval` always re-evaluates (never returns cached results). To view existing results without recalculating, use `revolver eval results`.

## 6. Pydantic Data Models

```python
from pydantic import BaseModel, ConfigDict
from datetime import datetime

class InstanceResult(BaseModel):
    """Result of evaluating a single instance.
    Note: status uses "solved"/"failed"/"timeout" (matching SQLite CHECK constraint
    and spec-eval output). DES-003 InstanceTestResult uses "pass"/"fail"/"timeout"
    for problem testing. The difference is intentional: "solved/failed" reflects
    whether the evaluator produced a valid result, while "pass/fail" reflects
    whether the test assertion passed."""
    instance_id: str
    status: str                     # "solved" | "failed" | "timeout"
    metrics: dict[str, float] = {}  # Empty if failed/timeout
    error: str | None = None
    compute_time_s: float | None = None

class MetricAggregate(BaseModel):
    """Aggregate statistics for a single metric."""
    model_config = ConfigDict(frozen=True)

    mean: float
    min: float
    max: float
    p10: float
    p50: float
    p90: float
    std: float
    count: int

class EvalMetadata(BaseModel):
    """Evaluation session metadata."""
    model_config = ConfigDict(frozen=True)

    eval_id: str
    solution_id: str
    dataset_name: str
    instance_count: int
    instances_solved: int
    eval_time_s: float | None = None
    evaluated_at: datetime
    user_aggregates: dict[str, float] | None = None  # Legacy evaluate() global aggregation (D-006-g)

class ComputeTimeSummary(BaseModel):
    """Compute time statistics across all instances."""
    model_config = ConfigDict(frozen=True)

    mean_s: float
    max_s: float
    total_s: float

class EvalResult(BaseModel):
    """Full evaluation result returned to CLI.
    JSON serialization produces nested 'compute_time' matching spec-eval §2.1.
    When user_aggregates is present (legacy evaluate() mode), the CLI displays
    both 'Revolver aggregates' and 'User aggregates' sections."""
    metadata: EvalMetadata
    aggregates: dict[str, MetricAggregate]          # Revolver-computed from raw per-instance data
    user_aggregates: dict[str, float] | None = None # From legacy evaluate() global call (D-006-g)
    compute_time: ComputeTimeSummary | None = None

class EvalDetailResult(BaseModel):
    """Per-instance evaluation result for --per-instance output."""
    metadata: EvalMetadata
    instances: list[InstanceResult]
```

## 7. Storage

### 7.1 SQLite Only

Unlike `revolver run` which uses both files and SQLite, `revolver eval` stores results **only in SQLite**. There are no manifest files or filesystem artifacts for evaluations.

Tables used:
- `eval_metadata`: one row per evaluation session
- `eval_instances`: one row per (instance, metric) — N instances × M metrics rows per evaluation

### 7.2 Storage Example

For an evaluation with 100 instances and 2 metrics (`combined_score`, `makespan`):

```
eval_metadata: 1 row
eval_instances: 200 rows (100 instances × 2 metrics)
```

Query for aggregate display:
```sql
SELECT metric_name, value
FROM eval_instances
WHERE eval_id = :eval_id AND status = 'solved'
ORDER BY metric_name, instance_id;
```

Aggregates are then computed in Python from the result set.

### 7.3 Key Queries

#### Get evaluation for a (solution, dataset) pair
```sql
SELECT * FROM eval_metadata
WHERE solution_id = :solution_id
  AND (:dataset IS NULL OR dataset_name = :dataset)
ORDER BY evaluated_at DESC
LIMIT 1;
```

#### Get raw per-instance results
```sql
SELECT instance_id, metric_name, value, status, error_message, compute_time_s
FROM eval_instances
WHERE eval_id = :eval_id
ORDER BY instance_id, metric_name;
```

#### Check if evaluation exists (used by benchmark to skip re-eval)
```sql
SELECT eval_id FROM eval_metadata
WHERE solution_id = :solution_id AND dataset_name = :dataset_name
LIMIT 1;
```

## 8. Core Layer: Function Signatures

```python
# --- Evaluation ---
def evaluate_solution(
    solution_id_or_alias: str,
    dataset_name: str,
    timeout_s: int = 300,
    parallelism: int = 1,
    force: bool = False,
    on_progress: Callable[[int, int], None] | None = None,
    project_root: Path | None = None,
    *,
    warn_split: bool = True,
) -> EvalResult:
    """
    Evaluate a solution against a dataset.
    Resolves solution → run → program path, iterates instances,
    stores raw results, computes aggregates.
```

## 11. Design Decisions

### DD-01: Aggregates computed at read time, not stored

See §4.1 for full rationale. FR-EVL-006 specifies aggregates are computed at read time, not stored. DES-001 v0.2 §3.7 reflects this: `eval_metadata` stores session metadata only (no aggregate rows). The `eval_instances` table stores raw per-instance data from which aggregates are derived at display time.

### DD-02: Evaluator from problem version snapshot (FR-EVL-003)

The evaluator used for evaluation is always the one from the immutable problem version snapshot (`.revolver/problem/<version>/evaluator.py`), not the mutable working copy. This ensures:
- **Reproducibility**: same problem version → same evaluator → same results (given same data)
- **Isolation**: editing the working copy doesn't affect ongoing or future evaluations of existing versions

### DD-03: Immediate per-instance storage

Each instance result is stored in SQLite immediately after completion, not batched:
- **Resilience**: if the evaluation is interrupted, completed instances are preserved
- **Observability**: intermediate results can be queried during a long evaluation
- **Simplicity**: no in-memory accumulator to manage

Trade-off: more frequent SQLite writes. Mitigated by WAL mode and the fact that each write is a single INSERT (~0.1ms).

### DD-04: Re-evaluation with confirmation (D-006-a)

Running `revolver eval` on the same (solution, dataset) pair requires confirmation before deleting and replacing previous results:
- **Interactive mode**: prompt `"Re-evaluate? [y/N]"` — user can abort
- **`--json` mode**: error unless `--force` is provided
- **`--force` flag**: skip confirmation and re-evaluate silently

Alternatives considered:
- **Unconditional replace** (previous design): deletes without warning. Rejected: risk of accidental data loss, especially in scripted pipelines.
- **Keep history**: store multiple evaluations per (solution, dataset). Rejected: adds complexity (which eval to display by default?), and the evaluator is immutable so results should be identical.
- **Block re-evaluation**: error if results exist, no override. Rejected: prevents legitimate use cases (dataset modified, evaluator bug fixed in new problem version).

The confirmation approach balances safety (no accidental deletion) with usability (`--force` for scripts and automation).

### DD-05: Shared evaluator runner at `infra/evaluator_runner.py` (D-006-f resolved)

The subprocess-based instance evaluation logic is shared between `core.eval._evaluate_instance()` and `core.problem._test_instance()` (DES-003). Both:
- Run the evaluator in a subprocess with timeout
- Set `REVOLVER_INSTANCE_PATH` and `REVOLVER_INSTANCE_ID`
- Collect `dict[str, float]` result

The difference: `problem test` loads the mutable evaluator, while `eval` loads the snapshot evaluator. The subprocess wrapper is the same.

**Resolution**: The shared implementation lives at `infra/evaluator_runner.py`. This is an infrastructure-level concern (subprocess management, timeout enforcement, environment variable handling) rather than a core-level concern. Both `core/eval.py` and `core/problem.py` call this shared runner.

### DD-06: Evaluator detection priority — evaluate() over evaluate_instance() (D-005-a)

When both `evaluate()` and `evaluate_instance()` are present in the evaluator module, `evaluate()` takes precedence:

1. If `evaluate()` exists → use it (legacy mode with `REVOLVER_INSTANCE_PATH`)
2. Else if `evaluate_instance()` exists → use it (Revolver mode with direct call)
3. Else → error

**Rationale**: If the user defined both functions, `evaluate()` is the "complete" implementation. The user may call `evaluate_instance()` internally from `evaluate()` for instance-level logic while adding orchestration or aggregation in `evaluate()`. Revolver should not bypass that orchestration by calling `evaluate_instance()` directly.

This is the reverse of the initial design (v0.1) which prioritized `evaluate_instance()`. The change was motivated by reviewing real-world evaluator patterns during D-005-a.

### DD-07: Legacy global aggregation step (D-006-g)

For legacy evaluators (`evaluate()` mode), after per-instance evaluation, one additional global `evaluate()` call retrieves the user's custom aggregates:

- **Per-instance**: `evaluate()` called with `REVOLVER_INSTANCE_PATH` per instance → per-instance metrics
- **Global**: `evaluate()` called without `REVOLVER_INSTANCE_PATH`, with `REVOLVER_DATASET_DIR` → custom aggregates (e.g., `combined_score`)

The custom aggregates are stored in `eval_metadata.user_aggregates` as JSON. This allows `revolver eval results` and `revolver benchmark` to display both Revolver-computed aggregates (mean, p10, p90...) and the user's own aggregation logic side by side.

For `evaluate_instance()` mode, this step is skipped — no global aggregation is available.

**Rationale**: Revolver's per-instance aggregation (mean, p50, etc.) may differ from the user's intended scoring (e.g., weighted average, min-based). Rather than guessing or overriding, we let both coexist and show them separately.

The schema has undergone two rounds of changes:

**Round 2** (v0.2 — Run/Solution refactor): `runs` table added as first-class entity, `solutions` simplified to (run_id, rank) reference, `solution_lineage` removed, `user_aggregates TEXT` column added to `eval_metadata`.

All updates completed in DES-001 v0.2:
- [x] DES-001 §2 ER diagram → `runs` + simplified `solutions`, `eval_metadata` with `user_aggregates`
- [x] DES-001 §3.5 (new) → `runs` table definition
- [x] DES-001 §3.6 → `solutions` table simplified (run_id, rank, alias)
- [x] DES-001 §3.7 → `eval_metadata` with `user_aggregates TEXT` column
- [x] DES-001 §3.8 → `eval_instances` FK unchanged (references `eval_metadata`)
- [x] DES-001 §6 → queries updated for run-based joins
- [x] DES-001 §9 → design decisions updated for run/solution split

### Impact on `core/benchmark.py`

With aggregates no longer stored in SQLite, `revolver benchmark` must compute aggregates in Python from raw `eval_instances` data. The `compute_aggregates()` function (§4.3) is reusable:
- `core/benchmark.py` loads raw per-instance data for each solution via `db.get_eval_instances()`
- Calls `compute_aggregates()` to produce per-solution, per-metric statistics
- Builds the comparative table from these aggregates

This is consistent with spec-benchmark FR-BEN-004 ("per-metric aggregate statistics computed from raw per-instance data") and FR-BEN-006 ("per-instance data is read from eval results, single source of truth").
